## 术语·用人话(被问到就这么解释)

- **MAPE(平均绝对百分比误差)**:每餐估的热量跟真值差百分之多少,取绝对值,再全部平均。说白了就是"平均每次估错百分之多少"。MAPE 25% = 平均每餐估错四分之一。
- **中位数误差(median APE)**:把每餐的误差从小到大排,取**最中间**那个。比平均数靠谱,因为不会被个别离谱的(比如某餐错 300%)带歪。我平均和中位都报,**中位才是"典型一餐"的体感**。
- **零样本 / zero-shot**:模型在 A 数据集上训好,**直接搬到 B 用,完全没看过 B 的答案、也没拿 B 调过**。能成说明是真泛化,不是死记硬背。
- **域内重标定**:拿目标场景自己的标准答案(称重真值)再调一遍模型。但**生产里没人给食物称重**,所以做不到——这就是"零样本"为什么关键。
- **份量符号翻转**:模型估份量时,**小份的估多、大份的估少**,方向正好反过来。这个规律在每个数据集都成立,是我最稳的一个发现。
- **几何平均(geomean)**:两个数相乘再开根号(√(a×b))。误差是"成倍数"的时候它比普通平均好,能把两个估计各自的极端错误**对冲**掉。
- **校正器(corrector)**:flash 先给个粗估,我再拿一个小模型结合深度体积去**纠偏**——不是重新识别,是"在 flash 基础上打补丁"。
- **随机森林 / 树集成**:一堆决策树投票取平均的机器学习模型,轻量、快(<1 毫秒),适合做这种打补丁。
- **外推**:模型碰到训练时没见过的数值范围。树模型这时会"卡住"输出常数、推不出去——这是校正器单独跨数据集会崩的根因。
- **内参 / fx(焦距,单位像素)**:相机的标定参数,决定"画面里一个像素对应现实里多大"。有它 + 距离,就能把像素换算成厘米、算体积。
- **AVDepthData / 深度图**:iOS 给的深度数据,本质是一张"每个像素离相机多少米"的图。
- **LiDAR / ToF**:iPhone Pro 上的激光测距传感器,能直接测**绝对距离**(厘米级)。
- **pgvector / HNSW**:把食物、食谱变成一串数字(向量)存进数据库;HNSW 是一种"快速找最相似向量"的索引,用来做"猜你喜欢"的召回。
- **pg_trgm(模糊匹配)**:把字符串切成"连续三个字母一组",比重合度判断两个词像不像。用来把模型说的食物名匹配到数据库条目(因为几乎从不一模一样)。
- **responseSchema(结构化输出)**:逼大模型必须按我给的 JSON 格式吐结果,不许自由发挥,保证后端能稳定解析。
- **thinking(思考模式)**:Gemini 2.5 会先"想"一大段再回答,更准但慢(~11 秒)。我关掉它,因为这个任务上它只加延迟、不加准。
- **OOM / heap(堆)**:heap 是 Java 程序能用的内存上限;设小了并发一上来内存就爆(OOM,被系统杀掉)。
- **P90 / P99**:延迟排序后第 90 / 99 个百分位。P90 = 3.7s 就是"90% 的请求快于 3.7 秒"。

# Part 1 — 项目介绍(直接开口说)

> 被问"介绍一下你的项目"时,1 分多钟讲出来。技术栈和数据集放最后,被追问再掏。

我做的是一个叫 Metriful 的健康饮食 App,卖点一句话能说清:**拍张照就能记这顿饭的热量**,不用像传统那些 App 那样手动一个个去搜数据库。技术上前端用 React Native,一套代码同时跑 iOS 和 Web,后端是 Spring Boot,识别和估热量主要靠 Gemini。

不过我在这个项目里花时间最多、自己也觉得最有意思的,其实不是把功能堆出来,而是去较真一件事——**这个"拍照估热量",到底准不准。**

说白了,你跟用户讲"我们 AI 能算热量",可要是误差有一倍,那这功能就是个摆设。但项目里之前从来没人量化过它的精度。所以我做的第一件事,就是找了个学术界有秤重真值的标准数据集,把我们 App 线上那套提示词和模型,原封不动跑上去测了一遍。

结果挺打脸的——**线上模型误差中位数有 51%**,基本就是瞎猜。但我没把这事盖过去,而是顺着往下挖:误差到底出在哪?拆解之后发现,模型其实**菜认得很准,但判断不出"到底有多少克"**——份量才是误差的大头。

而份量这东西,光看一张平面照片本来就判断不出来,得有物理尺寸信息。所以我就想到用 **iPhone 的 LiDAR 深度**:拍照的时候顺手测一下食物的体积,把这个绝对尺寸喂给模型去校正。

中间踩了不少坑——比如直接拿食物名查营养数据库,误差反而从 88% 干到了 176%;比如把深度当成文字提示喂给模型,模型根本不理。这些细节后面可以展开。最后真正跑通的方案是:**用快的 Gemini 2.5 flash(关掉它的思考模式,保证 4 秒内出结果),再加一个轻量的深度校正模型做融合**,把误差从 50% 多压到了 **25% 左右**,而且全程卡在 5 秒以内。

最后我还专门验了泛化:我前后一共在**五个数据集**上评估过——其中**三个有深度/体积的,不重新标定,误差都稳定在 25% 左右**;另外两个是平面、没深度的,正好反过来证明了"没有绝对深度,这套校正就会失效"。这块我自己觉得是整个项目里最硬的部分。

### 技术栈速记(被问到再展开)
- **前端** RN 0.81 / Expo 54 / TS;**后端** Spring Boot 3.3 / Java 21;**数据** PostgreSQL(pgvector)+ Redis(可选)+ Cloudflare R2;**AI** Gemini(识别/目标生成)+ OpenAI Embedding(向量召回);**部署** GCP Cloud Run + GitHub Actions,登录用 OAuth2(Apple/Google)+ JWT。
- **拍照→热量这条链路**:相机+LiDAR 拍照、顺手采一次深度 → 端上算体积(深度图→估出桌面那个平面→把食物高度乘以每像素面积加起来)→ 后端把图压到 1024 像素 → Gemini 2.5 flash(关思考)吐 JSON → `几何平均(flash 估值, 深度校正器)` → 校正后的热量。
- **一句话直觉**:`热量 = 每克多少卡 × 多少克`,误差几乎全在"多少克"(份量)上,而份量恰恰是单张照片看不出、深度能补的——这就是整个方案的出发点。

### 数据集全景(被问"测了几个/哪些")
前后一共测了 **5 个**公开数据集,分两组看:

| 数据集 | 有没有深度 | 它干嘛用的 / 结果 |
|---|---|---|
| **Nutrition5k**(食堂菜,秤重) | ✅ 有 | 测出 51%、定位到份量、用来训校正器;自己域内 34→25 |
| **MetaFood3D**(转盘扫描,秤重) | ✅ 有 | 第二个带深度集,零样本 30.3→24.7;几何换个传感器也准(相关 0.86) |
| **SimpleFood45**(真手机拍,西餐,量过体积) | ✅ 有 | 第三个带深度集,零样本 27.2→25.0 |
| **NutritionVerse-Real**(家常菜,iPhone,秤重) | ❌ 没有 | 负对照:在它上面校正**反而更糟**(31.5→35–38)→ 证明深度是必需的 |
| **MenuMatch**(餐厅菜,3 个菜系) | ❌ 没有 | 用来验证"份量符号翻转"跨菜系成立;那个"28→14.5"是特例,**已经证伪剔除了** |

> 一句话:**3 个带深度的 → 校正稳定 ~25%(零样本);2 个没深度的 → 既验证了诊断、又是反证(没深度校正就废)**。两组合起来才完整——不是"深度有用"一句话,而是"有深度→25%、没深度→失效",正反都测了。

# Part 2 — 难点 → 我怎么解决的

> 每条都是:难在哪 / 我怎么做的 / 结果。讲的时候按这个节奏说就行。

## 难点 1:"AI 能估热量"——可到底准不准,没人知道
- **难在哪**:产品天天说能估热量,但从没量化过精度,既没法优化,出了问题也没法负责。
- **我怎么做的**:找了个学术界的标准数据集 Nutrition5k,它每道菜都用秤称过、有真实热量。我把线上那套提示词+模型原样跑上去逐道菜对比。这里还有个坑:线上用的免费额度一天只能调 20 次,根本测不动,我切到付费的 Vertex AI 才跑通。
- **结果**:线上模型误差中位数 **51%**(平均每餐估错一半),是我测的所有模型里最差的。如实报,不美化。

## 难点 2:误差到底在"认菜"还是"估份量"?
- **难在哪**:不知道往哪使劲。
- **我怎么做的**:热量 = 每克多少卡 × 多少克。我分别假设"份量完美"和"每克卡路里完美",各算一遍误差,看哪个是大头。
- **结果**:份量给对了,误差降到 24–33%;每克卡路里给对了,只降到 ~50%。所以**份量是大头,认菜和密度都是次要的**。结论:**主攻份量(=深度),别折腾密度(=查数据库)。**

## 难点 3:几个"看着该有用"的招,全失效了(失败实验,主动讲反而加分)
- **难在哪**:直觉上,查营养数据库接地、强化提示词、多次采样投票,这些都该有用。
- **我怎么做的+结果**(都真测了,不是拍脑袋):

| 试的招 | 结果 | 为什么不行 |
|---|---|---|
| 直接拿食物名查 USDA 数据库 × 克数 | 88% → **176% 更糟** | 模糊匹配会抓错条目(番茄 → 番茄粉,差 6 倍),而且密度本来就是次要误差 |
| 把深度当文字提示喂给模型("画面宽 36cm") | 没变化 | 模型不会把"36 厘米"翻译成"所以是多少克" |
| 强化提示词(让它算上隐藏的油) | 31.5 → 31.6,没用 | — |
| 多次采样取中位(K=5) | 25.6 → 28.8 更糟 | 它每次答得差不多(波动才 10%),没有分歧可以平均掉 |
| 用单目深度(普通照片估深度)代替 LiDAR | 31.5 → 46 更糟 | 单目深度是相对的、没有绝对尺度,消歧不了份量 |

- **一句话洞察**:精度得**替模型算出来**(体积→克数),不能光**提示**给它。

## 难点 4:又要准、又要快(必须 5 秒内)
- **难在哪**:最准的 Gemini 2.5 pro 中位误差 26%,但一次要 **~22 秒**,破了 5 秒预算,而且 API 不让关它的思考模式;最快的 flash-lite 又最不准。
- **我怎么做的**:① 把模型从 flash-lite 换成 **Gemini 2.5 flash 并关掉思考模式**(实测思考模式只加延迟、不加准);② 把图压到 1024 像素再上传;③ 校正器推理 <1 毫秒,基本不占时间。
- **结果**:flash 关思考 ~34% 中位、~4 秒;**生产 1024 像素下,延迟中位 3.2–3.6 秒、P90 3.7–3.8 秒、几乎 100% 在 5 秒内**(原图不压是 4.67 秒,所以压图很关键)。pro 只当"异步精修"或"天花板参照",不上 5 秒主链路。

## 难点 5(核心):跨数据集泛化——零样本 25%,还不许重新标定
- **难在哪**:校正器在 Nutrition5k 自己域内 34→25 有效,**但生产里没人给食物称重,没法重新标定**。而且我早期直接把校正器搬到新数据集,误差 **36%(更糟)**,看起来"参数根本迁不过去"。
- **我怎么做的**:先搞清楚那 36% 是**过拟合**(树太深、死记了原数据集的数值范围)。然后两招:① **加正则**(树别长太深),让它别死记;② **跟 flash 做几何平均融合**——校正器单独还是迁不动(树不能外推),但**和 flash 一融合就行了**。原理是这俩的错误"方向不一样"(flash 错在份量、校正器错在外推),几何平均能互相对冲掉极端错误。
- **结果(三个独立带深度数据集,同一个校正器,零样本,不重新标定)**:

| 数据集 | 体积哪来的 | flash 原始 | + 校正器 |
|---|---|---|---|
| Nutrition5k(参照) | RealSense 深度 | 33.7% | **24.7%**(域内) |
| MetaFood3D(转盘扫描) | 扫描仪 3D 点云 | 30.3% | **24.7%** |
| SimpleFood45(真手机照·西餐) | 量过的体积 | 27.2% | **25.0%** |

三个全收敛到 ~25%,换 5 个随机种子都稳。**几何这条管线换个传感器也成立**:MetaFood3D 上点云算的体积 vs 真实体积,相关性 0.86。

## 难点 6:LiDAR 真的接到端上(不是占位代码)
- **难在哪**:之前那版用相机库的"帧处理器"去读深度——**死路**,因为这个库根本不把深度数据交给帧处理器。
- **我怎么做的**:改成一个**按需的原生模块**——拍照那一下临时开一个只取深度的小相机会话,采一次就关,顺便在手机上把体积/面积/高度算好,塞进给后端的元数据里,喂给校正器。
- **结果**:类型检查 0 错,前端 100 个测试 + 后端 381 个测试全过。真机编译还需要在一台带 LiDAR 的 iPhone 上 `eas build`(模拟器没深度硬件,测不了)——这条我会主动说。

## 难点 7:后端压测直接 503 崩了
- **难在哪**:拿 100 个请求压,**92 个返回 503**(成功 8 个就崩)。
- **我怎么做的**:查出根因——容器只给 512MB、Java 堆还写死 512MB、并发设到 80、最小实例 0,一并发就内存爆(OOM)被杀。修法:容器加到 2GB/2 核、并发降到 8、最小实例 1,堆改成按容器内存的百分比自动算,HTTP 连接池放大。
- **诚实补充**:其实真正的头号故障是那个**免费额度一天全站只能 20 次**——这才是用户最常遇到的失败,修法是上付费 Vertex。

# Part 3 — 深挖问答(每个答案都用人话)

## 3.A 关于 AI / 模型(会被往死里问)

**Q:你老说 MAPE、中位数,到底啥意思?**
MAPE 就是"平均每餐估错百分之多少"。中位数误差是把所有餐的误差排个序、取最中间那个——我更看重中位数,因为平均数会被个别错得离谱的(比如某餐错 300%)带歪,中位数才代表"普通一餐"的体感。所以我两个都报。

**Q:融合为什么用几何平均,不用普通平均?**
因为我们的误差是"成倍数"的——估成 2 倍和估成一半,严重程度其实一样。几何平均(相乘开根号)对这种倍数误差是对称的,而且能把两个估计各自的极端错误对冲掉:一个估高 2 倍、另一个估得准,结果就是 1.4 倍,误差从 100% 砍到 40%。

**Q:凭啥说 flash 和校正器的错误"方向不一样"?有证据吗?**
有。它俩犯错的原因不同:flash 错在份量(小份估多大份估少),校正器错在外推(碰到没见过的数值范围就乱)。证据是消融实验——**把深度特征去掉,融合就退回跟 flash 一样(没增益);加上深度才赚**。说明赚的是深度带来的"新信息",不是简单平均。

**Q:为什么校正器单独迁不过去,非得融合?**
因为它是树模型。树预测靠"落到哪个叶子取那群训练样本的平均",一旦输入超出训练见过的范围,它就只能输出边界那个常数,**外推不出去**。换个数据集数值分布一变,它就乱。融合时让 flash 把它拉回来,就稳了。

**Q:这 25% 会不会是你在那个数据集上反复调出来的?**
不会。融合权重就是 0.5(几何平均默认,没调);用的是最简版;换 5 个随机种子都稳(±0.2)。最关键的是——**我在第三个完全独立的数据集 SimpleFood45 上又复现了 25.0%**,不同来源、不同拍法。三个一致我才敢报。

**Q:过拟合到底多严重?**
单棵随机森林:训练集误差 15%、留出测试 27%,差了 12 个点,确实有点过拟合。但**留出的那个 27% 在各种验证方式下都一致**(干净测试集 26.8%、留一法 27.7%、5 折跑 6 个种子 26.0%±0.9),说明它是真实泛化水平。再做集成能降到 25.8%。所以我报的是泛化数,不是运气好的某一刀。

**Q:Nutrition5k 跟真实手机照差很多吧?会不会高估了难度?**
反过来。Nutrition5k 是俯拍、背景干净、份量还小(平均才 213 卡),其实**比真实手机照更难**。佐证:SimpleFood45 是真手机照,flash 原始误差 27% < Nutrition5k 的 34%——真实照确实更简单。所以我的数偏保守。

**Q:25% 够用吗?用户感受得到吗?**
一餐 500 卡,误差 ±125 卡左右。我们的定位是**低摩擦的粗估 + 趋势**,不是精确到卡。对减脂、控糖的人,**能坚持记录**比单次精确更重要;再加个一键调份量(½/1/1.5 倍)收个尾。我不会吹"精准营养"。

## 3.B iOS · LiDAR / ARKit 怎么集成的(iOS 面试官重点)

> 诚实状态:JS/几何这边类型检查+单测都过;**Swift 原生模块写完、自动链接也配好了,但最终真机编译要在带 LiDAR 的 iPhone 上 `eas build`**(模拟器没深度硬件)——这条我主动说,不假装"已真机跑通"。

**先讲我怎么选的路。** iOS 上拿深度有三条路,我一条条权衡:
1. **拍照接口自带深度**(`AVCapturePhotoOutput` 开 `isDepthDataDeliveryEnabled`):同一帧把照片和深度一起给你,最干净。但前提是整条相机都归我管——可我们用的是第三方相机库 vision-camera,走这条等于把它整个换掉,代价太大。
2. **ARKit 的场景深度**(`frameSemantics = .sceneDepth`):给的是稠密 LiDAR 深度,还自带相机内参,质量最好。但 ARKit 会话要独占相机,**跟相机预览打架**,而且重、起步慢。
3. **自己起一个只取深度的小会话**(`AVCaptureDepthDataOutput`)——跟相机库解耦,拍照瞬间临时开、采一次就关。**最终选这条**,集成代价最小。

所以 LiDAR 走第 3 条;对**有 ARKit 但没 LiDAR 的中端机**,我留了 ARKit 那条做降级(检测桌面平面、从画面中心打一条射线量到桌面的距离)。按设备能力分三档。

**Q:为什么用第三方相机库 vision-camera,不用苹果原生 / expo-camera?**
RN/Expo 上拍照有三档:**expo-camera**(官方)简单但弱,拿不到实时帧、不能选格式分辨率、控制粒度低;**vision-camera**(第三方、事实标准)给你实时帧处理、格式精选、高清拍照、底层控制——我们的"实时距离 reticle + 高清捕获"全靠它;**自己从零写 AVFoundation 相机**则要重做预览/拍照/方向/权限/生命周期,工作量巨大还丢了 RN 集成。所以选 vision-camera 是性价比最高的。**讽刺的是它偏偏不暴露深度**,所以深度我才单独开个原生小模块绕过去——它在扛预览/拍照那些重活,我只缺深度这一个旁路信号,没必要为它把整套相机重写。

**Q(追问):那你深度都写原生 Swift 了,相机为什么不干脆全用苹果原生自己写?**
分四层:
1. **整个 App 是 React Native(要 iOS + Web 一套代码)**,这是产品决定。所以相机必须融进 RN:预览是 RN 组件、拍照结果回 JS、reticle 是 React 画的。纯原生写相机,我得把预览(原生 UIView 包成 Fabric 组件)、拍照、方向、权限、闪光、变焦、生命周期、格式选择**全部桥接回 RN**——那基本是把 vision-camera 重写一遍。
2. **vision-camera 已经把这 95%(预览/拍照/UX)做好且接进 RN 了**,我只缺它不做的 5%(深度)。为这 5% 把整套相机原生重写,ROI 太差。
3. **关键:深度这块我恰恰就是用苹果原生的**——`AVCaptureDepthDataOutput` / `builtInLiDARDepthCamera` 都是 AVFoundation。所以不是"避开苹果 API",而是**在苹果 API 真正值钱的地方(LiDAR)用原生,通用相机管线用成熟库**。
4. **取舍交底**:如果这是原生优先的 app,我会直接走方案 1(`AVCapturePhotoOutput` 开 `isDepthDataDeliveryEnabled`,照片+深度同帧拿),那最干净。但既然产品是 RN,"vision-camera + 一个聚焦的原生深度模块"就是这约束下的最优解——而且**深度本身没妥协,就是原生 Swift**。

**Q(再追问):苹果不是有相机管线吗?为啥不直接用?**
这个问题把两件事混了,我会先点破:**苹果的相机管线就是 AVFoundation(`AVCaptureSession`/`AVCapturePhotoOutput`/`AVCaptureVideoPreviewLayer`),而 vision-camera 底层调的就是它——它不是另起炉灶,就是苹果管线的 RN 封装。所以我没绕开苹果管线。**
- **相机引擎**:用 vision-camera ≈ 用苹果的,只是别人把"接到 JS"那层写好了。
- **"直接用"在 RN 里没有零成本版本**:AVFoundation 是原生 API,不跟 JavaScript 说话。要在 RN 里直接用,必须有人把预览(原生 `UIView`→Fabric 组件)、拍照回调→JS、权限、方向、生命周期全桥接过去——这正是 vision-camera 干完且经过大量机型验证的活;我"直接用"就等于自己重写这层。
- **深度我恰恰就是直连苹果管线**:`AVCaptureDepthDataOutput` 是 AVFoundation 原生,这块没经过 vision-camera。所以一个项目里两种都有:通用相机走"封装好的苹果管线",深度走"我自己直连的苹果管线"。
- **一句话**:预览拍照走的是**封装好的** AVFoundation,深度走的是我**自己直连的** AVFoundation;在 RN 里"直接用"等于把那层桥接重写一遍,没必要。

**Q:为什么不用相机库的帧处理器读深度?**
因为那个库**只把视频帧给帧处理器,不给深度数据**。老代码想从帧的"附件"里捞深度,永远是空的,死路。所以深度必须自己单独开会话拿。

**Q:那个深度小会话具体怎么配?**(iOS 细节)
开个 `AVCaptureSession`,加 LiDAR 那个摄像头作输入,加 `AVCaptureDepthDataOutput` 作输出,打开它的滤波(对深度空洞做平滑)。深度格式从设备支持的里挑 32 位浮点那个。回调挂在一个**专用的后台串行队列**上,不放主线程(`startRunning` 是阻塞的)。

**Q:深度数据怎么变成"距离多少厘米"?为什么要锁内存/读中心/取中位/×100?**
回调里拿到 `AVDepthData`,转成 32 位浮点,它的 `depthDataMap` 本质就是"每个像素离相机多少米"的一张图。处理分四步,每步都有原因:
- **锁内存**:`depthDataMap` 是 `CVPixelBuffer`,硬件/GPU backed 内存。CPU 要读原始字节**必须先 `CVPixelBufferLockBaseAddress` 锁住**,否则指针无效——是 API 硬性要求(读完 `defer` 解锁)。
- **读中心一小块**:用户对着食物拍,**食物在画面中心**,中心深度 ≈ 相机到食物的距离,正是我要的;边缘都是桌面/背景,没用。
- **取中位数**:深度图有噪声和"空洞"(反光、边缘测不到 = 0/无效)。单读一个像素可能正好是空洞或离群点;**取一小块的中位数最稳**(中位天然忽略离群,平均会被异常值带歪)。
- **×100**:`AVDepthData` 深度单位是**米**,我整条管线用厘米,所以 ×100。

**Q:相机焦距 fx 哪来的?苹果自带?为什么要按分辨率缩放?**
**是苹果自带的**:`AVDepthData.cameraCalibrationData`(`AVCameraCalibrationData`)是 AVFoundation 直接给的,相机出厂就标定好了——我不自己算,只是读 `intrinsicMatrix[0][0]` 当 fx。要缩放是因为:这套内参是按某个"参考分辨率"(`intrinsicMatrixReferenceDimensions`,比如全尺寸 4032px 宽)定的,我的深度图可能只有 640px 宽,fx 随分辨率线性变,所以 `fx_我的 = fx参考 × 我的宽 / 参考宽`。好处:算"画面真实宽度 = 距离 × 宽 ÷ fx"时,代入后 = 距离 × 参考宽 / fx参考,**不管用哪个分辨率结果都一样**(自洽)。这个 fx 同时也用来算每像素的现实面积,做体积积分。

**Q:怎么知道这次深度可不可信?**
深度数据有个精度标志,`.absolute`(校准过的 LiDAR 绝对深度)就给高置信度,`.relative` 给低的。读不到就直接返回"没深度",后端退回默认盘子宽度——**绝不编一个假数出来**。

**Q:你这个深度会话跟相机预览不抢摄像头吗?**
会抢。**同一个摄像头同一时刻只能被一个会话占用**。所以我用"拍照瞬间开→采几帧→立刻关"的短生命周期,采完马上把摄像头还回去。代价是预览那 ~0.5 秒可能轻微卡一下,能接受。

**Q:Expo 托管工程怎么让 JS 调到你的 Swift?(注意:这步是桥接,不是苹果自带)**
JS 要调原生 Swift,中间得有个"桥"。老办法是写一堆 Objective-C 胶水 + bridging header,啰嗦、且新架构在淘汰。我用的是 **Expo Modules API**:直接写个 Swift 类声明 `measure` 异步方法,Expo 框架**自动生成 JS↔原生的绑定**(新架构下走 JSI),样板代码少。"链接"= 构建时怎么找到我的模块:放一个配置文件 + podspec,Podfile 里的 `use_expo_modules!` 自动发现,**不用手改 Xcode 工程文件、不用写 config plugin**。JS 侧 `requireNativeModule('MetrifulLidar')`,web/安卓/Expo Go 上模块不存在就自动降级"没深度"。一句话:**这是让 JS 调到我那段 Swift LiDAR 代码最省事的现代方式。**

**Q:手机上的体积到底怎么算的?公式写清楚——是深度除以 fx 吗?**
对,就是深度除以 fx。针孔相机原理:深度 `Z` 处,**一个像素对应的现实尺寸 = `Z / fx`**(米/像素)。所以(单位米):
```
每像素现实面积 = (Z / fx)²          # Z=该像素深度, fx=焦距(像素)
每像素高度    = plane − Z           # plane=桌面深度;食物更近(Z 更小)→高度为正
体积 = Σ(食物像素) (plane − Z) × (Z / fx)²     # 单位 m³,再 ×1e6 → cm³
```
其中 `plane`(桌面平面)取深度图**边缘一圈的中位数**;食物像素 = 中心区里高度 > 0.5cm 的。直觉:`Z/fx` 是这个像素在那个距离上现实多大,平方=面积,乘以高度 `(plane−Z)` 就是这根"柱子"的体积,所有食物像素加起来 = 总体积。

**Q:为什么非得绝对深度,普通照片估的深度不行?**
体积得是绝对的立方厘米,才能定份量。普通照片估的深度是"相对"的、没有绝对尺度,定不了份量——实测加进去反而 31.5→46% 更糟。LiDAR 给的是绝对距离,体积才真,校正器才有用。这就是为什么 LiDAR 是核心、不是装饰。

**Q:哪些 iPhone 有 LiDAR?系统要求?怎么降级?**
iPhone 12 Pro/Pro Max 往后的 Pro 系列,加 2020 年后的 iPad Pro。我用的那个 LiDAR 摄像头接口要 iOS 15.4 以上,代码里加了版本判断。三档降级:有 LiDAR(±1cm)→ 有 ARKit 没 LiDAR(±3cm)→ 都没有(后端用默认盘宽,±5cm)。

**Q:模拟器测不了你怎么验证的?("离线管线"指什么?)**
"离线管线"就是我在 `scratchpad/eval/` 里那套 **Python 评测代码**(`geom_depth.py`):在电脑上、在基准数据集(Nutrition5k/MetaFood3D)上算体积,对应的是**端上**(手机里 Swift 实时算)。验证分两层,我会**分清楚说**:① 离线那套自己做过等价自测(`geom_depth.py` 复现原始 `build_features.py`,299/300 特征 2% 内一致),这是 **Python 对 Python**;② 端上 Swift **照搬了这条已验证的公式**,但**没在真机上跟 Python 数值逐一对过**(没设备/Xcode 跑不了)。所以准确说法是"Swift 用的是已验证的离线公式",不是"Swift 已和离线对平"——真机数值验证还要 `eas build` 上 LiDAR iPhone。这条我不夸大。

## 3.C 后端 / 数据库

### 数据库设计(被问到能展开讲)

整体是 PostgreSQL,一共 **52 个 Flyway 迁移**(就是版本化的建表脚本,V1→V52,每次结构改动都能追溯)。设计上我会讲几条原则:**业务数据都按用户维度切分**;**语义搜索用向量、模糊搜索用 trigram**;**高频读的营养字段做反规范化**(从 JSONB 抽成物化列);**前面挡多级缓存**减数据库压力。

**核心表(讲的时候挑 3–4 张说就行):**

| 表 | 关键列 | 为什么这么设计 |
|---|---|---|
| `users` | UUID 主键、email 唯一、`auth_provider` 枚举(本地/Google/Apple)、apple 用户 id、连续打卡天数、最后活跃日 | UUID 不暴露自增量(防爬);打卡天数直接落用户上,首页一次读完 |
| `user_profile` | 和 users **1:1**(共享主键)、身高体重、健身目标/饮食偏好/健康模式(枚举)、每日热量+三大宏量目标、BMI/体脂/基础代谢 | 跟账号拆开,因为档案字段多、更新频率不一样 |
| `food_nutrition` | 每 100 克的热量/蛋白/脂肪/碳水(`BigDecimal(8,2)` 精确)、food_key 上建 trigram 索引 | **本地营养主源**,V52 灌了 ~7800 条 USDA;trigram 索引支持模糊查名字 |
| `meal_log` | 餐类型(早午晚加餐)、食物明细 `foodItems`(JSONB)、图片 URL、用餐时间、整餐营养汇总 | 一餐多个食物用 JSONB 存,省得单拆明细表;整餐营养冗余一份,避免每次聚合 |
| `recipe` / `exercise_videos` | 营养摘要 JSONB、**1536 维向量**、目标标签数组;recipe 还有从 JSONB 抽的**生成列** | 向量做推荐召回;生成列让热量等字段能直接查、能建索引 |
| `user_goals` | 目标类型、每日热量(最小/目标/最大)、宏量、运动量目标、里程碑(JSONB)、`(user_id, is_active)` 上**部分唯一索引** | 部分唯一索引保证"每个用户同时只有一个激活目标" |
| `weight_log` | 体重、日期、体脂、肌肉量、`(user_id, 日期)` 唯一、`(user_id, 日期 DESC)` 索引 | 时序数据,唯一约束防一天多条,倒序索引让"最近 N 天"查得快 |

**几个我会主动拿出来讲的设计决策(显深度):**
1. **向量推荐**:食谱/视频用 OpenAI 把"名字+描述+分类"变成 1536 维向量存进去,建 **HNSW 索引**(参数 m=16、ef_construction=64,余弦距离 `<=>` 算子)。还挂了个触发器:入库前自动拼好那段文本再生成向量,省得应用层操心。
2. **生成列做反规范化**:食谱营养原本塞在一个 JSONB 大字段里,我把热量/蛋白/碳水抽成数据库的 `GENERATED ALWAYS AS ... STORED` 物化列——查询不用每次解 JSON,还能建索引,排序过滤快很多。
3. **投影 + EntityGraph 治 N+1 和内存**:列表查询用轻量投影,**故意不带那个 6KB 的向量列**(线上是小机器,省内存);取食谱带食材时用 EntityGraph 一次 JOIN 拉全,避免 N+1(一条主查询拖出 N 条子查询)。
4. **USDA 表删了又接回(演进故事,面试爱听)**:早期建过一套 USDA 表,后来 **V44 大清理**把它和一堆没做起来的功能(购物清单、姿态分析、旧反馈表)一起删了,改成本地 `food_nutrition` + Gemini 识别;再后来"体积→密度"又要查营养,我**重新接回** USDA 接口,但这次是**接口 + 两级缓存放在应用层**,不再建 DB 表。这条能讲清"为什么删、为什么又回来"。
5. **外键级联**:meal_log、user_goals、weight_log 都挂在用户上,删用户级联清理,不留孤儿数据。

**Q:数据库怎么设计的?(一句话版)**
PostgreSQL + 52 个 Flyway 迁移;按用户切分,向量(pgvector/HNSW)做推荐、trigram 做模糊匹配、JSONB+生成列做反规范化、多级缓存挡读。详见上表。

**Q:pgvector、HNSW 是干嘛的?**
做"猜你喜欢"。把食谱、运动视频用 OpenAI 的 embedding 变成 1536 个数字的向量存进去,HNSW 是一种快速找"最相似向量"的索引,查的时候按余弦距离找最近的几个推给用户。比另一种索引(ivfflat)召回质量好。

**Q:pg_trgm 模糊匹配是什么?为什么需要?**
把字符串切成"每三个字母一组",比两个词重合多少来判断像不像,阈值设 0.3。需要它是因为模型说的食物名跟数据库条目几乎从不一模一样。**但它也会抓错**(番茄→番茄粉)——这正是前面"直接查数据库"那招崩到 176% 的原因之一。

**Q:多级缓存挂了怎么办?**
两级:进程内的 Caffeine(热数据,十几分钟过期)+ 可选的 Redis(多实例共享)。**本地那张 7800 条的食物表才是主力**,查不到才去调 USDA 接口。Redis 挂了就降级到本地缓存 + 直接查,**不影响请求成功**——缓存挂了不能拖垮主流程。生产上其实没开 Redis,走 Caffeine 就够。

**Q:为什么有些列是"生成列"?**
食谱的营养原本存在一个 JSONB 大字段里。我把热量、蛋白、碳水这些抽成数据库的"生成列"(自动从 JSONB 算好存下来),这样查询不用每次解析 JSON,还能建索引,快很多。

**Q:503 那次到底咋回事?**
容器内存只给了 512MB、Java 堆还写死 512MB、并发开到 80、最小实例 0。一上并发,图片解码 + 多个模型请求一起来,内存直接爆(OOM)被杀。修法:容器 2GB/2 核、并发降到 8、最小实例 1、堆改成按容器内存比例自动算。

**Q:有没有安全问题?**(主动交底)
有。我发现所有线上密钥——**包括数据库密码**——都是 Cloud Run 的明文环境变量,没走密钥管理服务。这是我标出来要修的。说明我 review 的时候是带着安全视角看的。

## 3.D 延迟 / 系统

**Q:5 秒内怎么保证的?你测的是什么?**
三招:关思考模式(开着 ~11 秒,破预算还不加准)、图压到 1024 像素(原图 4.67 秒 → 压完 3.2 秒)、超时设得短(主请求 8 秒、重试 6 秒,快速失败)。几何 + 校正器加起来 <10 毫秒,基本不占时间。**实测中位 3.2–3.6 秒、P90 3.7–3.8 秒,几乎全在 5 秒内**。诚实说:这是**单请求的中位/P90,不是高并发压测的 P99**;高并发靠 Cloud Run 自动扩容兜。

**Q:有个 20.7 秒的怎么回事?**
那是一次**网络重试**(碰到临时错误,我的代码退避等了几秒重发),不是单次推理慢。正常调用都是 2.4–5 秒。生产配了付费额度后,重试很少见。

## 3.E 产品 / 取舍

**Q:为什么不做全自动,非要用户确认份量?**
因为份量是误差大头,一键 ½/1/1.5 倍是**最便宜的精度提升**,而且是行业标准做法(MyFitnessPal、Noom 都这么干)。低摩擦不等于假装精确。

**Q:这个校正器能直接上生产吗?**
模型已经导出了,后端推理步骤也写好了。但**生产里没有称重真值做域内标定**,所以我用的就是零样本融合(已经在 3 个数据集验证了 ~25%),**不假设能重新标定**——这恰恰是这套方法的价值:不依赖目标场景的标定。后端 Java 加载这个模型,要么重写树集成,要么转成 ONNX。

**Q:接下来还会做什么?**
蒸馏一个真正的图像端专用小模型(文献上能到 13–16%,又准又快);搭一条"在生产里慢慢攒标定数据"的闭环(份量确认、扫条形码、愿意称重的重度用户);再扩到混合餐盘(现在两个带深度集都是单一食物)。

# Part 4 — 不足 & 改进(被问"短板/重做怎么改"时)

> 这部分主动讲,显自我认知。先说最诚实的两条,再分点。**会用人话承认边界,比假装完美在严谨面试里安全得多。**

## 最大的两个不足(先说这两条)

**1. 校正器目前没真正跑在生产里,只在离线验证。**
模型导出了、后端推理步骤也写好了,但 Java 服务还没把它加载进去;**更根本的是生产没有称重真值,没法在生产域内标定**。我现在用的是"零样本融合"(已在 3 个数据集验证 ~25%)绕过这个问题,但这毕竟是"基准上的 25%",不等于"线上用户实测 25%"——这俩我会分清楚,不混着说。

**2. LiDAR 这条端上链路还没在真机上编译验证过。**
JS 和几何那边类型检查 + 单测都过了,Swift 模块也写完、自动链接配好了,**但模拟器没深度硬件,真机编译要在一台带 LiDAR 的 iPhone 上 `eas build`**,我还没跑。所以我会说"代码写完了、就绪了",不会说"已经在真机上跑通了"。

## 其余不足(被追问再展开)

- **只测了单一食物,没测混合餐盘。** 三个带深度数据集要么是转盘单物体、要么是单份食物;真实场景是一个盘子里好几样菜叠在一起,我那套"整体体积"分不开每样,这块没验证。
- **泛化只在"插值域"成立。** 校正在"目标份量范围跟训练数据重叠"时管用(真实餐食 100–800 卡基本满足);要是全是 2000 卡的巨无霸大份(完全超出训练范围),会退化。
- **延迟测的是单请求,不是高并发 P99。** 中位 3.2–3.6 秒是单请求的;高并发下的尾延迟没压测过。而且真实头号故障其实是那个"免费额度一天 20 次",这个比延迟更要命。
- **数据偏西餐 + 样本偏小。** 没有中餐/亚洲菜的"带深度 + 标注"数据(中餐混合多、酱汁多,更难);而且 MetaFood3D 才 98、SimpleFood45 才 38 个样本,统计噪声不小(Nutrition5k 976 才是大样本)。
- **深度只用了"整体体积",没做逐项分割。** 没有"先把每样食物分割出来、再各算体积各查密度",所以多食物场景天然受限。
- **安全:线上密钥是明文环境变量**(含数据库密码),应该走密钥管理服务——发现了但还没修。

## 如果重做 / 继续做(按性价比排)

1. **搭"生产标定数据闭环"**(最关键)。用户一键确认份量(½/1/1.5 倍)= 弱标签、扫条形码 = 已知热量锚点、餐厅菜单热量、愿意称重的重度用户 = 稀疏真值。攒够域内标签,就能训一个**真正贴生产分布**的校正器,而不是只靠零样本。
2. **几何升级:分割 + 逐项体积。** 用分割模型(比如 SAM)把盘子里每样食物抠出来,逐样算体积、查密度——既更准,又能处理混合餐盘,直接解掉上面那个最大限制。
3. **蒸馏一个图像端专用小模型。** 文献上微调/蒸馏在 Nutrition5k 能到 13–16%,又准又快——巨型通用 LLM 是这种窄任务的错误工具。这是把误差从 25% 往 15% 推的路。
4. **置信度分级**:简单菜走 flash 快路径;模糊/低置信的升级到 pro 异步精修,或直接让用户确认。把慢路径只留给真需要的那 ~10%。
5. **相似餐缓存**:用已有的 pgvector,按图像/餐相似度缓存,重复吃的餐零模型成本秒回。
6. **后端真正集成校正器** + 真机验证 LiDAR + 灰度 A/B 量化真实收益;**安全**上把密钥迁到 Secret Manager。
