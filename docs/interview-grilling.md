## Part 0 — 一句话与三个亮点

**一句话:** 一个 AI-first 的健康/营养 App(React Native + Spring Boot),核心是"拍照→识别食物→估算热量",我做的最有价值的工作是 **把这个 AI 功能的真实精度量化测出来,定位误差来源,并在 <5s 延迟预算内把误差砍掉约一半**。

**面试主动交底的三个亮点(按可信度排序,这是头号叙事):**

1. **诊断 > 调参。** 我在三个独立西餐基准上验证了一个稳定的误差结构(份量偏差的**符号翻转**:小份高估、大份低估)。这个诊断跨采集方式、跨菜系、跨厨房都成立 —— 它是泛化的资产,**比任何一组校正参数都值钱**。
2. **量化了"什么有效、什么无效",而不是只报喜。** 模型选择是主杠杆;而几个"看起来该有效"的算法杠杆(naive USDA grounding、depth 作 prompt hint、prompt 强化、self-consistency)实测全部无效或更糟。我会主动讲这些**失败实验**。
3. **在延迟预算内达标。** 训练了一个 9 特征的轻量校正层(RandomForest 集成,<1ms 推理),把 `gemini-2.5-flash` 的热量误差从 51% 中位数压到 **25.8% 中位数(leave-one-out)**,~4.2s,**追平了 `pro` 的 26% 但只用 1/5 的延迟**。

> ⚠️ **第一句就要交底的边界**(否则被拷打会很被动):
>
> - "34→26%" 的事后校正 **只在带深度的 Nutrition5k 上成立**;无深度的 2D 数据集上事后校正全部失败。
> - "<5s" 是**单请求**延迟,不是压测下的 P99。
> - 端上只做 **深度→尺度** 的一行几何换算,体积/质量的几何积分是离线设想,**没上线**。
> - 深度精度说"**厘米级**",不要吹"<1%"。
> - `pro` 的 26% 是**异步精修/benchmark 天花板**,不是 <5s 关键路径上的方案。

## Part 1 — 项目介绍(技术骨架)

### 1.1 架构总览

```
Frontend  React Native 0.81 / Expo 54 / TS 5.9  (iOS + Web)
Backend   Spring Boot 3.3.5 / Java 21 / Gradle
Data      PostgreSQL(+pgvector) · Redis · Cloudflare R2(S3 兼容)
AI        Gemini Vision(拍照识别) · Gemini LLM(目标生成) · OpenAI Embeddings(向量召回)
Infra     GCP Cloud Run(au-southeast2) · GitHub Actions → Docker → Cloud Run · OAuth2(Apple/Google)+JWT
```

### 1.2 拍照→热量 的真实数据流

```
[相机] 拍照 + 读深度(LiDAR/ToF/ARKit)
   │   端上: estimateImageWidthCm() —— 把"相机到食物的距离"换算成"整帧的真实宽度 img_w_cm"(针孔模型,一行公式)
   ▼
[后端 GeminiMealAnalysisService]
   │   图像压缩 → Gemini Vision(responseSchema 强约束 JSON)→ {食物名, 估算质量 g, 每项营养}
   │   超时 8s 主调用 / 6s 重试,OkHttp dispatcher 并发控制
   ▼
[NutritionLookupService]
   │   本地 food_nutrition 表(pg_trgm 模糊匹配,USDA SR Legacy ~7.8k 条 seed)为主源
   │   miss → USDA FoodData Central API(两级缓存:Caffeine L1 + 可选 Redis L2)
   ▼
[返回] 食物 + 热量 + 宏量营养
```

关键:`kcal = density(每克热量) × mass(克数)`。**误差几乎全在 mass(份量)上**,density 是次要项 —— 这是后面所有结论的基石。

### 1.3 我实际改/写了什么

- **eval harness(核心工作量)**:`n5k_eval.py` 等,把 App 的真实 prompt + responseSchema 通过 Vertex AI 打到三个基准的真值上,产出 MAPE/中位 APE/命中率/逐请求延迟。
- **特征校正层(Solution B)**:9 特征 RandomForest 集成(RF + ExtraTrees + GBR),log 目标,leave-one-out + clean split 双验证。
- **后端可扩展性修复**:Cloud Run `2Gi/2cpu/concurrency=8/min=1/max=30/cpu-boost`;JVM 堆改 `MaxRAMPercentage=65`(原来 512Mi 盒子上写死 `-Xmx512m`);OkHttp `maxRequestsPerHost 5→128`。解决 503 雪崩。
- **USDA 两级缓存**:`UsdaFoodDataClient` + `UsdaNutritionCache`(Caffeine L1 + 可选 Redis L2),作为本地表 miss 的 fallback 重新接回(V44 曾删)。
- **端上尺度模块** `scale.ts`:深度 → `img_w_cm`,针孔/FOV 双公式,带边界 clamp(12–90cm)和"读不到深度就返回 null、不编数"的降级。

## Part 2 — 核心拷打:AI 精度(这是会被往死里问的地方)

### Q1. "你说能 AI 识别热量,到底准不准?给个数。"

**答:** 生产模型(当时是 `gemini-2.5-flash-lite`)在 Nutrition5k 上实测 **~51% 中位 / 88% 均值**热量误差 —— 是我测的所有模型里最差的。我没有拿这个数去包装,而是去定位为什么差、怎么修。修完后(快路径方案)中位误差降到 **~26%**。

**拷打点应对:**

- 为什么用中位数?→ 因为均值被长尾(个别 300%+ 的离群)严重拉高,中位数才是"典型用户"的体感。我两个都报。
- 这是不是挑了简单数据?→ 反过来。Nutrition5k 是俯拍、中性背景、小份食堂菜(均值 213 kcal),**比真实手机照更难**。文献上 ~25% 的 LLM 数字多是在更简单的餐前手机照数据集(如 ACETADA)上。我的数字偏保守。

### Q2. "误差到底在哪?你怎么知道是份量不是识别?"

**答:** 因为 `kcal = density × mass`,我对每个模型算了两个**反事实天花板**:

- "如果份量完美" → 误差降到 24–33%(density 残差)
- "如果 density 完美" → 误差只降到 ~50%(份量残差)

→ **份量(mass)误差主导,density 次要。** 模型很会认"这是什么菜",但**单图判断不出多少克**。这把优化方向钉死了:攻份量,别攻 density。

### Q3. "那你最稳的发现是什么?(让我看你真懂)"

**答:份量偏差的符号翻转。** 三个独立基准全部验证:

- 小份/中份 → **高估**(N5k +12~16%)
- 大份西餐 → **低估**(NutritionVerse 大份 tertile `pred/gt`=0.66,MenuMatch Italian 0.72)

这个结构跨采集者、跨菜系、跨厨房都成立。**它是我整个工作里最泛化的资产** —— 因为它是"诊断",不是"拟合出来的参数"。一个模型系统性地把大份往小里压、把小份往大里抬,这是可解释、可利用的。

### Q4. "那些'该有效'的算法优化,你试了吗?"(失败实验,主动讲)

主动报四个**无效/更糟**的实验 —— 这是加分项,证明我测了而不是猜:

| 杠杆                                                           | 结果                               | 为什么失败                                                                                |
| -------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------- |
| Naive USDA grounding(LLM 报食物名+质量 → USDA 每100g × 质量) | 88% →**176%(更糟)**         | 首条匹配抓错条目("tomato"→"tomato powder" 302kcal/100g)。而且 density 本来就是次要误差。 |
| Depth 作 prompt hint(把真实`img_w_cm` 喂进 prompt)           | ~中性(45%→40%,n=40)               | 模型不会把"画面宽 36cm"翻译成"所以是 X 克"。**精度得替模型算出来,不能只是提示它。** |
| Prompt 强化(显式提示隐藏油脂 + 份量 CoT)                       | 31.5% → 31.6%,无效                | ——                                                                                      |
| Self-consistency(K=5,temp 0.5,取中位)                          | 28.8% vs 单次 25.6%,**更差** | 样本 CV 仅 ~10%,没有方差可聚合,反而引入噪声。                                             |

**核心洞察:** 两个"算法捷径"都假设模型会**利用**结构化的旁路信息自我纠正;实测它基本不会。**精度必须替模型计算出来(体积→质量、DB 查询),而不是提示给它。**

### Q5. "那你最后是怎么达标的?"

**答:** 一个轻量**特征校正层**(不是视觉模型)。在 `gemini-2.5-flash`(关掉 thinking,~4.2s)输出之上,用 9 个便宜特征训一个 RandomForest 集成:

> flash 报的 kcal、mass、item 数、深度体积/面积/高度、主食物的 USDA 每100g、flash 隐含的 kcal/g……

| 方案                            | 均值 | **中位**  | ±25%命中 | 延迟           | ≤5s |
| ------------------------------- | ---- | --------------- | --------- | -------------- | ---- |
| 原生产`flash-lite`            | 88%  | 51%             | 32%       | ~4s            | ✅   |
| `gemini-2.5-flash` 原始       | 48%  | 34%             | 37%       | ~4.2s          | ✅   |
| A — 2参数 log 线性校准(零训练) | 46%  | 34%             | 35%       | ~4.2s          | ✅   |
| B — 特征 RF                    | 39%  | 27%             | 47%       | ~4.2s          | ✅   |
| **B+ — RF 集成**         | 38%  | **25.8%** | 49%       | ~4.2s          | ✅   |
| (参考)`gemini-2.5-pro`        | 39%  | 26%             | 47%       | **~22s** | ❌   |

**结论:集成校正层 25.8% 中位(LOO),追平 `pro` 的 26%,但延迟只有 1/5。** 推理 <1ms,几乎不加延迟。

### Q6. "RandomForest 是不是过拟合了?train 多少 test 多少?"(必被问)

**主动交底:** 单 RF 的 train 中位 15% vs held-out 27%,**有 ~12pp 的过拟合 gap**。但 held-out 数字**跨验证方案稳定**:

- clean 100-dish test:26.8%
- leave-one-out over 400:27.7%
- 5-fold × 6 seeds:**26.0% ± 0.9**

三者收敛 → 27% 是可信的泛化数,不是 lucky split。**集成把方差压下来**,LOO 中位 27.0% → 25.8%(两种集成变体一致)。所以我报 25.8% 是站得住的。

### Q7. "这个校正泛化到别的数据集吗?"(最容易翻车,必须主动交底)

**精确交底:泛化的是"方法 + ~25% 天花板",不泛化的是"冻结的参数"。我在第二个独立带深度数据集上验证过。**

分三种情况讲(这是我亲手测的):

1. **2D 无深度数据(NutritionVerse / MenuMatch)→ 校正失败。** 零样本 N5k 树 35.5%、few-shot 33–50%、域内 5-fold 37.8%,**全部比 raw 31.5% 更差**。无绝对尺度无法消歧份量,误差方差主导。→ 证明**没有绝对深度就没有校正**。
2. **第二个带深度数据(MetaFood3D,637 个物体,真秤重 + 真 3D 点云)→ 校正成功。** 我重新搭了几何管线(点云→体积)、跑 flash、做校正:
   - **几何管线换个传感器也对**:点云算的体积 vs GT 体积,log-log 相关 **0.86**(N5k 的 RealSense → MetaFood3D 的 Revopoint,同一套管线都成立)。
   - **域内校正**:raw flash 31.0% → **+深度 24.9%(LOO)/ 24.8%±1.3(5折×6种子)**;**去掉深度就没有增益**(31.7%)。深度特征重要性 **0.38**,比 N5k 的 0.16 还高 —— 单物体份量变化大,flash 更看不出绝对大小。
   - **两个独立带深度数据集收敛到 ~25%**(N5k 34→25,MetaFood3D 31→25)。
3. **但 N5k 训的参数零样本迁到 MetaFood3D → 36%(更差)。** 混合餐盘→单物体的分布漂移,冻结模型迁不过去。

**所以一句话:泛化的是 ①诊断(符号翻转,3 集)②"flash + 绝对深度几何 + 校正"这套方法 ③~25% 这个天花板(2 个独立带深度集验证)。不泛化的是某一组拟合系数 —— 每个域要各自标定。** 生产 App 永远有 LiDAR/ToF 深度,所以这条路可部署;但我不会把一个冻结模型当万能。

- ⚠️ "15 个西餐样本 28→14.5%" **是 MenuMatch Italian 特例**(均匀乘性偏差),已被 NutritionVerse 证伪 —— 简历删了,绝不当泛化卖点。
- ⚠️ MetaFood3D 是单物体转盘扫描(非混合餐盘),热量是 FNDDS 算的(质量是真秤的),n=98 —— 这些边界我都会主动说。

### Q8. "为什么不直接用 pro?26% 多好。"

**答:** `pro` 实测确实能泛化(三集一致降误差:N5k 45→30、Italian 28→22、NutritionVerse 31.5→27.3,平均 ~26%),**但它是 thinking 模型,每张图 15–30s,直接破 <5s 预算**,而且 API 不让关它的 thinking。交互式记餐用户不会等 20 多秒。所以 `pro` 在我的方案里是**异步精修选项 / benchmark 天花板**,不是 <5s 关键路径。快路径留给 flash + 深度校正。

### Q9. "深度到底用来干嘛?精度多少?"

**答(注意措辞):** 端上只做一步:把相机到食物的**距离**换算成**整帧真实宽度** `img_w_cm`(针孔模型 `img_w_cm = distanceCm × frameWidthPx / fxPx`,或 FOV 版),目的是**打破单目尺度模糊** —— 让模型知道场景物理多大,而不是靠"食物占画面比例"瞎猜。

- 精度量级是**厘米级**,不吹 "<1%"。
- 我用物理 sanity check 验证过深度标定:`桌面深度 − 食物深度 = 4–7cm`(合理的盘装食物高度),确认了 0.1mm 深度单位和 ~33–36cm 相机高度。
- **重要边界:** 真正的"分割食物→体积积分→质量"几何管线是我提的**离线设想,没上线**。当前线上只有这一行尺度换算。而且把它作 prompt hint 实测是中性的(Q4)—— 正确做法是几何算出质量,而不是把宽度提示给模型。
- **单目深度(Depth-Anything-V2)替代不了:** 实测加进校正器反而 31.5%→46% **更糟**,因为相对深度没有绝对尺度,无法消歧份量翻转。**这正说明 LiDAR/ToF 的绝对深度是精度护城河,不是装饰。**

### Q9b. "生产没有称重真值、没法域内标定,只有深度 —— 那 flash + 校正器在生产真能 25% 吗?"(最尖锐,必须诚实)

**诚实答:不能。25% 是带称重真值的「域内标定」结果,不是生产 SLA。** 我把边界测穿了:

- 校正器**零样本跨域更差**(N5k 参数 → MetaFood3D:31→36)。
- 连**不需要真值的确定性几何路径**我也实测了 —— 也不行:`深度体积 × 密度 × USDA能量`,ρ=1 物理版 **99–118%**;加一个 *oracle* 全局标量也只有 **38.6%**(仍 > flash 31%);几何与 flash 融合 32%(≈flash,无提升)。
- **为什么不行**:体积→热量需要"质量密度、系统偏差"这些**标定量**,不是纯物理常数能定;三个噪声因子相乘误差爆炸 + 食物名→密度匹配噪声(和 naive USDA grounding 176% 同一个病)。

**所以生产能落地的真相(分三层,主动讲):**

1. **唯一零真值就能改善的**:模型升级(已上线,N5k ~34%;真实手机照比 N5k 简单,可能更接近 25–30%,**但我没在野外测过,不 claim**)。
2. **深度要兑现 25% → 必须有标定数据**。生产没有称重,所以要**自建标定闭环**:用户份量确认(½/1/1.5×)=弱标签、条形码/包装食品=已知热量锚点、餐厅菜单热量、愿意称重的重度用户(T2D 群体)=稀疏真值 → 攒够域内标签再训校正器。
3. **这才是真正的工程难点 —— 不是模型,是标定数据闭环。**

**一句话兜底:** "我证明了这套方法有 ~25% 的天花板(带深度 + 标定),也诚实测了**没有标定时深度兑不了现**(确定性路径比 flash 还差)。所以生产路线是:模型升级先吃掉一半误差,再用产品手段(份量确认/条形码/重度用户)逐步攒标定数据 —— 而不是假装一个离线 25% 能直接搬上线。" 这比硬吹"我们生产 25%"在严谨面试里安全一个量级,且显示我分得清 **benchmark 数 vs 生产 SLA**。

## Part 3 — 后端/系统拷打

### Q10. "你说 Redis 多级缓存,具体缓存什么?挂了怎么办?"

**答:** USDA FoodData Central 查询结果,两级:Caffeine(进程内 L1,热点)+ Redis(共享 L2)。

- **本地 `food_nutrition` 表(pg_trgm 模糊匹配,USDA SR Legacy ~7.8k 条 seed)才是主源**,USDA API 只是本地 miss 时的 fallback。
- Redis 是**可选**的:挂了降级到 L1 + loader,不影响请求成功 —— 缓存层失败不能拖垮主路径。

**为什么本地表 seed USDA 而不是只查 API?** 又快(本地 trigram 索引)、又准(就是 USDA 数据)、还无外部依赖。这是最干净的修法 —— 之前手写几十条不够,直接 seed USDA 核心 ~7.8k 条替掉。

### Q11. "pg_trgm 模糊匹配是什么?为什么不精确匹配?"

**答:** trigram(三元组)相似度。把字符串切成连续 3 字符片段,按重合比例算相似度,配 GIN/GiST 索引。用它是因为 LLM 报的食物名和 DB 条目几乎从不字面相等("grilled chicken breast" vs "Chicken, broilers or fryers, breast, grilled")。模糊匹配能召回,但 **Q4 的教训:模糊匹配也会抓错(tomato→tomato powder)**,所以 density grounding 不是免费午餐,需要好的匹配 + 它本来就是次要误差。

### Q12. "你提到 503,讲讲怎么排查和修的。"

**答:** 100 请求压测打生产,~8 个成功后 **92× HTTP 503**。根因:`512Mi` 容器 + 写死 `-Xmx512m` 堆 + 默认 concurrency 80 + `min-instances 0` —— 并发图像解码 + hedged Gemini 调用直接 OOM-kill。
**修:** Cloud Run `2Gi/2cpu/concurrency=8/min=1/max=30/cpu-boost`;堆改 `MaxRAMPercentage=65`(让堆跟着容器内存走,别写死);OkHttp `maxRequestsPerHost 5→128`。
**但我会同时讲真正的 #1 故障源:** 生产用的是 **free-tier Gemini key,全站每天总共只能 ~20 次扫描**就硬失败 —— 这才是用户侧失败的头号原因,不是 Cloud Run 尺寸。修法是上 paid Vertex/billing。

### Q13. "安全方面有没有发现问题?"

**主动交底(诚实加分):** 调查时发现**所有生产 secret —— 包括生产 DB 密码、R2 keys、所有 API key —— 都是 Cloud Run 明文环境变量**,不是 Secret Manager 引用。这是我标为需要修的安全发现。报告里明确写了。(说明我 review 时是带着安全视角的,不是只看功能。)

## Part 4 — 产品/取舍拷打

### Q14. "为什么不让用户手动确认份量,非要 AI 猜?"

**答:** 应该让。份量是主误差(Q2),一键 ½×/1×/1.5× 确认是最便宜的精度提升,也是行业标准(MyFitnessPal、Noom)。这在我的建议清单里。AI 负责把摩擦降到"拍一张",但**最后一档份量校正交给用户**是对的产品取舍 —— 不要为了"全自动"的叙事牺牲精度。

### Q15. "这功能真能帮用户养成习惯吗?"(产品 sense)

**答:** 核心假设是**摩擦是放弃记录的头号原因**。传统 App 要手动搜数据库,我把它压到"拍一张<3s"。但我也清楚 AI 估算有 ~26% 误差,所以定位是"**低摩擦的粗估 + 趋势**",不是"精确到卡"。对减脂/T2D 用户,**一致地记录**比单次精确更重要 —— 趋势对了就有价值。这也是为什么我没有过度承诺精度。

## Part 5 — 反向拷打 / 一句话兜底

被问到不会的、或想收尾时:

- **"这个项目你最大的收获?"** → 学会**先量化再优化**,以及**主动报告失败实验和边界**。最值钱的产出不是某个数字,是"知道哪些杠杆有效、哪些是幻觉,以及结论的适用边界在哪"。
- **"如果继续做?"** → 蒸馏一个真正的**图像端 specialist**。文献上微调/蒸馏模型在 Nutrition5k 能到 **13–16%**,既比 `pro` 准又快。巨型通用 LLM 是窄而延迟敏感任务的错误工具。
- **被追到细节不确定时** → "这个我当时没测到,我能讲的是我**确实测过**的部分是 X,边界是 Y" —— 永远不编数。
